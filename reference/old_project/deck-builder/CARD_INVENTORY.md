# Card Inventory

Generated by read-only extraction from every `CardData` resource under
`resources/cards/`. Values are transcribed exactly as authored in each
`.tres` file — a field not written in the file is reported as its
script default (from `card_data.gd` / `card_effect.gd`), explicitly
marked `[default]`, never omitted.

> **2026-09-03:** the "Rogue" placeholder class was renamed to **Samurai**
> and its two throwaway cards — **Backstab** and **Shadow Step** (plus their
> `+` upgrade variants) — were deleted. The Samurai's card pool
> (`resources/cards/classes/samurai/`) is now empty. Group F below has been
> removed; other counts in this snapshot predate later card additions and
> are not re-derived here.

## Summary

1. **Total card count: 27** `CardData` resources are inventoried below
   (this is a curated snapshot, not a live folder count — several later
   `+` upgrade variants exist on disk but aren't tracked here).

2. **Existing upgrade-related field: yes.** `CardData.upgrades:
   Array[CardData] = []` (`card_data.gd:225`) — a list of full
   replacement `CardData` resources, not a tier/upgraded-flag/numeric
   delta. Empty means "cannot be upgraded." There is no separate
   `upgraded: bool` or `tier: int` field anywhere on `CardData`.

3. **How the shop's upgrade service resolves an upgrade:** it swaps to a
   separate, full `CardData` resource — confirmed in
   `card_upgrade_service.gd`. `offer_upgrade()` reads the chosen card's
   own `upgrades` array (`options := chosen.upgrades`), lets the player
   pick one if there's more than one, then calls
   `RunState.replace_card_in_deck(chosen, picked)` — a straight
   replacement of the deck slot's resource, no field-by-field delta
   applied anywhere. The replacement resources live in
   **`resources/cards/upgrades/`**, a flat folder outside every class's
   `card_pool_folder`, so they're never reachable as ordinary reward
   pulls — only ever reached via a base card's own `upgrades` array.

4. **Cards with an authored upgrade variant (at snapshot time): 4 of 27** —
   Slash → Slash+, Guard → Guard+, Bite Down → Bite Down+,
   Owed in Full → Owed in Full+. (More `+` variants have been authored
   since; this snapshot does not track them.)

## Orphans and dangling references

**Cards referenced in code or a pool with no corresponding resource
file:** none found. Every `res://resources/cards/...tres` path referenced
from any `.gd` or `.tres` file in the project (starter-deck preloads,
`upgrades` arrays, `chain_followup_effect`, the NPC-offer list) resolves
to a real file on disk — cross-checked by extracting every such path
string and diffing it against the actual file listing.

**Resource files not referenced anywhere:**
- `res://resources/cards/classes/wanderer/retired/heavy_blow.tres` (see
  Group E above — no direct path reference, and excluded from the
  folder-scan pool by living in a `retired/` subfolder).
- `res://resources/cards/classes/wanderer/retired/guard.tres` (2026-09-05,
  starter-deck rework — see Group E above; same shape as Heavy Blow, no
  direct path reference and excluded from the folder-scan pool).
- `res://resources/cards/upgrades/guard_plus.tres` is now the SAME kind
  of gap by extension, not by its own direct check: it's still
  referenced BY `guard.tres`'s own `upgrades` array (that reference is
  intact - a `res://` path survives a parent resource moving), but since
  nothing anywhere loads `guard.tres` any more, nothing ever reaches
  `guard_plus.tres` through that reference in practice either. Left in
  place at its own unchanged location, not moved - out of scope for the
  pass that retired Guard.

Every other card resource not reached by direct path reference (the
Group B Wanderer-pool cards) *is* reached — via
`CardPool.load_class_pool()`'s directory scan of its class's
`card_pool_folder` — so none of those count as unreferenced; they're
just discovered by folder listing rather than by name.
